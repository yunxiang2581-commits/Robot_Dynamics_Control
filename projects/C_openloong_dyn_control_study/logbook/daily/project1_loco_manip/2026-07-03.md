## 5. 排查链条

第一次 T4 首跑失败：

```text
run:
20260703_000648_walk_wbc_t4_inplace_visual_wslg

现象：
[T4-HOLD] drift_mm 逐步到 300-400 mm
30s base gps 约 [0.566, -0.345, 1.084]
```

根因判断：

- `xv_cmd=0` 只让期望速度为 0。
- 原 `walk_wbc.cpp` 每周期执行 `jsInterp.setIniPos(RobotState.q(0), RobotState.q(1), ...)`，导致 `base_pos_des` 跟着当前 base 漂移走。
- 对“世界固定手点”来说，base 慢慢漂走会把目标点推到手臂工作空间外。

第一次修正：

- T4 in-place 锁定 base XY/yaw 锚点。
- 结果 base 漂移被压住，但右手漂移仍在 `70-100 mm`。

第二次修正：

- 在同一个 `HandTrackJoints` slot 内加入行权重。
- 手位置行权重提高，右臂姿态正则减弱。
- 结果 T4 漂移降到 `max=15.642 mm`。

## 9. 同源反事实修复（补偿量化的方法学收口）

> 追加于 07-04 凌晨。§6 的初步量化只跑了 compensating 一条线；为回答“手任务到底补偿了多少”，需要一条 arm-locked 对照线，构成反事实。

### 9.1 缺陷：跨 binary 的脏对照

第一版反事实用的是：

```text
D_on  (compensating): 20260703_001752 run   (07-03 00:17 生成)
D_off (arm locked)  : 20260703_233220 run   (07-03 23:32 生成)
```

三个时间戳暴露问题：

```text
compensation run 001752  -> 07-03 00:17   旧 binary
walk_wbc binary  build   -> 07-03 23:20   中间重编译过
baseline run     233220  -> 07-03 23:32   新 binary
```

- `OPENLOONG_T4_BASELINE` 门控（`algorithm/hand_track_task.cpp:181/307-308`）是新代码，必须编译进 binary 才生效；baseline run 靠它跑出来，说明它用的是 23:20 的新 binary。
- 而 compensation run 跑在 00:17，比 binary 构建早 23 小时，用的是**旧 binary**（无 `T4_BASELINE` 门控、无 §1.5 magic-number env 化整改）。
- 结论：第一版反事实是「旧 binary 补偿线 vs 新 binary 基线线」，物理上大概率成立（整改是同值替换），但方法学上不是干净对照，审图人一比时间戳就露。

### 9.4 §1.5 整改无副作用的独立佐证

新旧两个 compensation run 是两次独立仿真、且跨了 binary（旧 001752 vs 新 003659），但 base 运动几乎逐位一致：

```text
comp_base_xy max       : 旧 63.793 -> 新 63.795   (差 0.002 mm)
base_xy_path_delta max : 旧 19.614 -> 新 19.615   (差 0.001 mm)
```

换了 binary、走了 §1.5 magic-number env 化整改，物理输出差 ~0.002 mm。这是「整改是同值替换、无副作用」的独立证据，也顺带落实了「§1.5 整改后未重新验证」这条挂账。

### 9.5 口径声明与遗留

- 口径：**matched-condition counterfactual**（same binary + same Xvfb long workflow + matched in-place condition），不是 bitwise 严格控制变量。诚实边界写在此，图脚注只放结论。
- 遗留（二阶精修，不阻塞）：base overlay (a) 显示 10-25s 两线高度重合、25s 后 arm-locked 线略微上抬分叉；可把稳态窗从 10-30s 收到 10-25s 避开分叉段，让结论更严。当前 10-30s 窗结论已足够稳。
