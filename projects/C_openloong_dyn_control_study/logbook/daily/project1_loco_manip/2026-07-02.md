## 5. 遇到的问题

- 问题：最初把右手世界目标在第 0 帧锁存，导致 stand-up transient 期间手位置变化被误记为 T1 漂移。
  - 现象：`[T1-HOLD] drift_mm` 从 0 增大到约 370 mm / 664 mm。
  - 初步原因：`walk_wbc.cpp` 在 `simTime <= 3s` 时直接下发初始化关节目标，WBC 输出被旁路；`simTime >= 3s` 后又切入 Walk，stand 分支没有稳定验证窗口。
  - 当前状态：增加 `OPENLOONG_T1_STAND_ONLY=1` 后，T1 stand-only smoke 中锁定后漂移日志为 0 mm。
- 问题：日志统计里的 `naninf=2` 容易误解。
  - 现象：T1 enabled 日志中匹配到 `inf`。
  - 初步原因：匹配到的是 qpOASES 的 `infeasible` 字符串，不是真正 NaN/Inf 数值；baseline 启动也会出现 QP 初始报错。
  - 当前状态：暂不作为 T1 失败依据，后续正式验证时应单独过滤 `nan` / 独立数值异常。
- 问题：可视仿真比短 smoke 暴露出 T1 stand-only 不稳定。
  - 现象：MuJoCo / WSLg 可视窗口可启动，仿真跑到 `simTime=10.574`；但 `[T1-HOLD] drift_mm` 后续扩大到 60 mm、580 mm、1500 mm 量级，并出现大量 qpOASES `Maximum number of working set recalculations performed`。
  - 初步原因：当前 3+7 维任务仍允许右手位置误差通过浮动基列和右臂列共同求解，且 stand-only 下全身姿态本身可能已经不稳定；短 smoke 只覆盖了锁定初期，没覆盖后续失稳。
  - 当前状态：可视运行证明“窗口和程序能跑”，但 T1 位置保持还不能算通过。

## 6. 今日理解

- 右手线速度雅可比非零列为 `0..5` 浮动基 + `13..18` 右臂列，说明右手任务索引方向正确。
- `q(7..13)` 对应左臂，`q(14..20)` 对应右臂；当前 10 维任务中尾部 7 维左臂保持用的是 `q.block<7,1>(7,0)`。
- T1 stand 验证不能直接用原始 `walk_wbc` 默认流程，因为默认流程 3s 后进入 stepping / walk；需要显式 stand-only 门控，才能验证 stand 分支中的笛卡尔手任务。
- 今天只证明了“可编译 + env 门控 + 短时 stand-only smoke”，还没有证明完整 T1 done-check。
- 可视仿真是必要的：短时 Xvfb smoke 给了早期 0 mm 漂移，但可视长一点跑才暴露出后续姿态/手任务失稳。

## 8. T1 收尾更新（夜间继续验证）

T1 后续继续排查后，最终结论需要覆盖上面第 5-7 节里的旧判断：

- 大漂移根因不是右手 `J_hd_r` 索引本身，而是 `OPENLOONG_T1_STAND_ONLY` 最初把原 demo 的 0-3s 姿态/步态准备流程截断后，没有在 3s 之后继续写正确的 `base_pos_des(2)`。
  结果是 stand WBC 的 `Pz` 任务把 base 往错误高度拉，姿态塌掉后右手世界点出现米级漂移。
- 修正方式：保留原 demo 前 3s PVT 姿态准备；3s 后在 T1 stand-only 中继续通过 `jsInterp.dataBusWrite` 写入固定 base 高度 `stand_legLength + foot_height = 1.08`；右手目标延后到约 3.5s 后锁定。
- 同时把右手任务的浮动基列清零：`J.topRows(3)=J_hd_r.topRows(3)` 后执行 `J.block(0,0,3,6).setZero()`，让右手保持主要由右臂完成，不让低优先级手任务借 base 漂移“解题”。
